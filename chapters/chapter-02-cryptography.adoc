== Criptografía

La criptografía es un pilar fundamental de los sistemas blockchain, las DLT, los contratos inteligentes y las criptomonedas. Este capítulo ofrece una visión general de la criptografía(((criptografía))) y su papel en la blockchain, centrándose en las funciones de hash(((función de hash))), las técnicas de cifrado(((cifrado))) y las firmas digitales(((firmas digitales))). Aunque los detalles técnicos profundos están fuera del alcance de este capítulo, al final se proporcionan recursos para una mayor exploración.

=== Funciones de hash

Al principio de la historia de la computación, se hizo evidente que los mensajes entre sistemas digitales pueden cambiar durante la transmisión debido a problemas con el medio de comunicación u otras razones. Encontrar una solución a este problema se volvió prioritario. Una solución inicial implicó agregar un bit de paridad adicional a los datos enviados entre dispositivos, sirviendo como una garantía de seguridad para verificar si los datos habían cambiado.

Un bit de computadora puede ser 0 o 1. Para una implementación ingenua de un bit de paridad, si el número total de bits establecidos en 1 en un paquete de datos es impar, entonces el bit de paridad se establece en 1; si es par, se establece en 0. Sin embargo, dado que el bit de paridad solo puede almacenar un único 0 o 1, existe una alta probabilidad de que ocurran errores sin ser detectados. Por ejemplo, si dos bits que originalmente eran 0 se alteraran a 1, el bit de paridad ingenuo seguiría pareciendo válido. Aunque existen mejores esquemas de paridad, siguen siendo insuficientes para las grandes cantidades de datos que se transmiten.

Basándose en este concepto, se introdujeron los checksums(((checksum))). A diferencia de los bits de paridad, que codifican información de verificación de integridad en un solo bit, los checksums utilizan tamaños de datos más grandes para codificar dichas verificaciones, que van desde uno hasta múltiples bytes.

De hecho, las verificaciones de integridad no solo son esenciales para garantizar la integridad de los datos, sino también para verificar que los datos no hayan sido alterados cuando se almacenan en el mismo dispositivo. Aunque los checksums son efectivos para proporcionar estas verificaciones de integridad, persiste el riesgo de errores no detectados. Este riesgo surge porque dos piezas de datos diferentes pueden producir el mismo valor de checksum.

Se necesitaba una verificación de integridad más efectiva, y ahí es donde entraron en juego los hashes. Los hashes sirven como verificaciones de integridad similares a los checksums, pero están diseñados para que sea (casi) imposible que una pieza de datos original y una versión alterada produzcan el mismo valor de hash. Pueden considerarse como huellas digitales únicas que identifican datos específicos. Dada cualquier entrada arbitraria, un algoritmo de hash producirá una huella digital única, o hash. La misma entrada producirá consistentemente la misma salida de hash.

Dicho de otra manera, el algoritmo producirá una huella digital única de tal manera que es (casi) imposible que dos entradas de datos diferentes generen el mismo hash. Si incluso un solo bit de los datos de entrada cambia, el hash de salida cambiará drásticamente. Al almacenar o enviar la huella digital con los datos originales, es posible verificar si los datos originales han sido alterados. Si han sido alterados, entonces la huella digital no coincidirá. Además, los algoritmos utilizados para generar hashes deben garantizar que sea (casi) imposible que una pieza de datos alterada y su huella digital asociada (hash) resulten en una coincidencia. De formas más concreta podemos decir que las funciones de hash(((función de hash))) proporcionan una solución que garantiza que una pieza de datos no ha cambiado en el tiempo y el espacio.

Las funciones de hash(((función de hash))) garantizan que los datos permanezcan sin cambios al almacenar el hash generado de los datos correspondientes. Mientras el hash permanezca intacto, se puede verificar que los datos asociados no han sido modificados.  Sin embargo, si alguien altera los datos y ajusta el hash para que coincida con los nuevos datos, el receptor no podría detectar este cambio.  

Discutiremos una solución a este problema más adelante en este capítulo.

Aunque las funciones de hash(((función de hash))) resuelven un problema significativo para los dispositivos de comunicación, no garantizan la _privacidad_ de los datos. Ahora exploraremos las técnicas de cifrado(((cifrado))) diseñadas para proporcionar privacidad de datos.

=== Técnicas de cifrado

Aunque las plataformas blockchain no utilizan principalmente técnicas de cifrado(((cifrado))) para garantizar la privacidad de los datos en el sentido tradicional, sí emplean estas técnicas para ofrecer otras garantías esenciales, que discutiremos más adelante en este capítulo.  

A continuación, presentamos una descripción general de las técnicas de cifrado(((cifrado))) para ayudar al lector a comprender mejor el contenido que se expondrá más adelante.

// Sin embargo, el cifrado y el descifrado son fundamentales para las firmas digitales.

Las técnicas de cifrado se propusieron originalmente para permitir la comunicación segura entre emisores y receptores, evitando que los espías descifraran o entendieran la información intercambiada. Estas técnicas se clasifican en cifrado _simétrico_ y _asimétrico_.

==== Cifrado simétrico

El cifrado utiliza claves tanto para cifrar (codificar) como para descifrar (desbloquear) datos. El cifrado simétrico emplea la misma clave para ambos procesos. Similar a una cerradura física, se utiliza la misma clave para cerrar y abrir, específicamente durante el cifrado(((cifrado))) y el descifrado. Esta clave digital se comparte entre las partes que se comunican, lo que generalmente requiere un intercambio previo a través de un medio de comunicación diferente.

Si un espía escucha la comunicación inicial donde se comparte la clave, puede descifrar mensajes futuros e inyectar mensajes cifrados sin que ninguna de las partes se dé cuenta. Esto ocurre porque el espía tendría acceso a la clave de cifrado/descifrado. Por lo tanto, es crucial compartir dichas claves de forma segura, asegurando que un espía no pueda interceptarlas.

- Los diferentes pasos del proceso se denotan con números en un recuadro azul.

- Las líneas discontinuas en la parte superior indican alguna forma de comunicación previa para acordar la clave compartida.

Los pasos involucrados en el proceso son los siguientes:

    * El paso 0 generalmente ocurre antes de que las partes se comuniquen a través del medio utilizado para transmitir datos cifrados. Las partes deben acordar una clave de cifrado(((cifrado)))/descifrado compartida, que se utilizará tanto para el cifrado como para el descifrado. Esta clave podría ser generada por la Parte A, la Parte B, o incluso generada en conjunto — no importa siempre que ambas partes tengan acceso a la misma clave compartida. Es importante tener en cuenta que cualquier parte que posea la clave específica puede tanto descifrar como cifrar mensajes.

    * Una vez que la parte emisora (en este caso, la Parte A) tiene la clave, puede cifrar los datos destinados a la otra parte aplicando el algoritmo de cifrado simétrico usando la clave, como se muestra en el paso 1. El algoritmo producirá los datos cifrados.

    * Después de eso, la Parte A, la parte emisora, transmitirá los datos cifrados generados en el paso 1 al destinatario previsto, la Parte B. Los espías no podrán descifrar los mensajes si la clave solo es conocida por las partes A y B, incluso si el mensaje de datos cifrados es interceptado por un espía footnote:[siempre que la fortaleza de la clave de cifrado/descifrado sea suficiente].

    * Al recibir los datos cifrados, la Parte B, la parte receptora, puede descifrarlos con la clave utilizando el algoritmo de descifrado.

La misma clave puede ser utilizada tanto por la Parte A como por la Parte B para cifrar y descifrar datos, permitiéndoles enviar y recibir mensajes de forma segura entre sí. Esta seguridad depende de que la clave permanezca confidencial y no se filtre a ningún tercero.

El cifrado simétrico(((cifrado))) es fácil de entender e implementar, ya que se basa en una única clave de cifrado/descifrado. Sin embargo, no ofrece garantías con respecto a:

- *Procedencia del mensaje* — cualquier parte con acceso a la clave compartida puede cifrar datos, lo que hace imposible determinar el remitente del mensaje cifrado.

- *Confidencialidad* — no hay seguridad de que los mensajes destinados a una parte específica sean vistos exclusivamente por esa parte.

==== Cifrado asimétrico

La introducción del _cifrado asimétrico_ en la década de 1970 proporcionó una solución más segura para mitigar a los posibles espías. Asegura que los mensajes solo puedan ser descifrados por el destinatario previsto. En el cifrado asimétrico(((cifrado asimétrico))), cada parte comunicante tiene dos claves:

- Una _clave pública_ asociada con el destinatario, que se hace pública. Cualquier parte que desee cifrar datos destinados al destinatario utilizará esta clave.

- Una _clave privada_ que el destinatario mantiene confidencial. Esta clave privada(((clave privada))) se utiliza para descifrar mensajes cifrados con su clave pública(((clave pública))).

Las claves pública y privada están íntimamente ligadas (de ahí el término par de claves(((par de claves))) ), y es imposible footnote:[o más bien computacionalmente inviable] derivar la clave privada a partir de la clave pública.

<<img_asym>> muestra una visión general de cómo funciona típicamente la comunicación con cifrado de clave asimétrica(((cifrado))). Las principales diferencias en el proceso se resaltan en rojo, y a continuación se describen los pasos involucrados:

* En lugar de requerir que el emisor y el receptor acuerden una clave de cifrado/descifrado compartida, el cifrado asimétrico(((cifrado asimétrico))) les permite divulgar sus claves públicas. Tanto el emisor como el receptor pueden hacer visibles sus claves públicas a todo el mundo sin preocupación. El paso 0 muestra cómo la clave pública de la Parte B es visible para la Parte A.

* La Parte A puede entonces cifrar mensajes destinados a la Parte B introduciendo los datos brutos (en este caso, 'Data2') junto con la clave pública de la Parte B(((clave pública))) en el algoritmo de cifrado asimétrico(((cifrado asimétrico))) (mostrado en el paso 1). El algoritmo de cifrado producirá los datos cifrados.

* Después de eso, la Parte A puede enviar los datos cifrados a la Parte B (mostrado en el paso 2), con la confianza de que solo la Parte B podrá descifrar los datos, ya que solo se pueden descifrar usando la clave privada de la Parte B(((clave privada))), que se mantiene confidencial.

* Finalmente, la Parte B puede introducir los datos cifrados recibidos y su clave privada en el algoritmo de descifrado (mostrado en el paso 3), que producirá el mensaje real destinado a ellos (que es 'Data2').

El cifrado asimétrico no permite que la Parte B envíe mensajes de vuelta a la Parte A usando la misma clave de cifrado/descifrado. Esto asegura que los mensajes destinados a una parte específica solo puedan ser descifrados por esa parte. Para responder, la Parte B simplemente usa la clave pública de la Parte A para cifrar mensajes.

Aunque el cifrado asimétrico(((cifrado asimétrico))) asegura que solo el destinatario previsto pueda descifrar un mensaje en particular, no impide que un remitente se haga pasar por otra persona. Esto también se aplica al cifrado de clave simétrica cuando la clave de cifrado/descifrado compartida se ve comprometida. Por ejemplo, consideremos un actor malicioso, la Parte C, que tiene acceso a la clave pública de la Parte B(((clave pública))). La Parte C podría cifrar mensajes destinados a la Parte B y enviarlos, afirmando falsamente ser la Parte A. La Parte B no tendría forma de identificar que los mensajes son en realidad de la Parte C. La solución a este problema son las _firmas digitales_, que se discutirán a continuación.

=== Firmas digitales

Las firmas digitales abordan el problema de la suplantación del remitente al permitir que cualquiera verifique que un mensaje fue creado y firmado digitalmente por una parte emisora específica y que el contenido permanece sin cambios. Las firmas digitales contienen dos componentes fundamentales: _cifrado de clave pública_ y _algoritmos de hash_. <<img_create_signature>> muestra el proceso de creación de una firma digital.

Crear una firma digital implica los siguientes pasos:

1. Un algoritmo de hash codifica el contenido del mensaje (p. ej., Hello), creando una huella digital única (hash) de los datos originales (p. ej., 185f...1969). Esta huella digital identifica de forma única el contenido original.

2. El hash resultante se cifra con la clave privada del remitente usando cifrado de clave pública. El hash cifrado es la firma digital (p. ej., c1f3...691c).

3. El remitente puede entonces transmitir el contenido del mensaje junto con la firma digital generada. A partir de entonces, cualquier destinatario puede verificar que el remitente creó el mensaje y que no ha sido alterado.

<<img_verify_signature>> muestra el proceso de verificación de una firma digital.

[caption="Figura {counter:figure}. ", reftext="Figura {figure}"]
.Una representación de cómo se verifican las firmas digitales.
[#img_verify_signature]
image::verify_signature.png[]

Verificar un mensaje firmado digitalmente implica los siguientes pasos:

1. El destinatario primero debe haber recibido el mensaje (p. ej., 'Hello') y la firma digital asociada (p. ej., c1f3...691c).

2. El destinatario luego descifra la firma digital usando la clave pública del remitente(((clave pública))). El valor descifrado debe ser el hash (huella digital única) del mensaje original (p. ej., 185f...1969 mostrado en la parte inferior derecha de <<img_verify_signature>>).

3. El destinatario calcula el hash del mensaje recibido y lo compara con el hash descifrado obtenido en el paso anterior. Si coinciden, el destinatario puede estar seguro de que el remitente creó el mensaje. Específicamente, el destinatario puede garantizar que el par de claves privada/pública(((clave pública))) del remitente(((par de claves))) se utilizó para generar la firma digital. Dado que la firma digital es el hash cifrado, y el hash identifica de forma única la pieza de datos específica, se puede confirmar que los datos no han sido alterados desde que se creó la firma digital y que se fueron creados por el remitente (usando su par de claves pública/privada).

La siguiente sección explora cómo los principales componentes criptográficos ayudan a mantener y asegurar los sistemas blockchain.

==== Funciones de hash

Las funciones de hash son fundamentales para las blockchains. A continuación se presentan algunos ejemplos específicos donde se utilizan funciones de hash en sistemas blockchain.

. *Identificador único de bloque* — las blockchains consisten en bloques de transacciones y otra información. Cada bloque está asociado con un identificador único, que se deriva usando una función de hash sobre los datos del bloque.

. *Identificador único de transacción* — las transacciones suelen estar asociadas con un hash de transacción, que es un identificador único de la transacción específica generado al codificar los datos de la transacción específica. A lo largo de este libro, se presentan diversos ejemplos de ésto.

. *Identificador de script* — los hashes se utilizan a menudo para identificar código/scripts de contratos inteligentes específicos — como se verá en varias partes del libro.

. *Para encadenar bloques* — los bloques se encadenan de manera inmutable haciendo que el bloque más reciente haga referencia al hash del bloque anterior. Si alguna información en el bloque anterior cambia, se nota inmediatamente porque el hash del bloque anterior ya no coincidiría con el hash almacenado en el bloque más reciente. De hecho, esta técnica no solo proporciona una solución para el bloque anterior, sino que también invalida el hash si cualquier parte del historial de bloques más antiguos se cambia, incluso ligeramente. En consecuencia, todos los bloques generados después del bloque respectivo y sus hashes también se invalidarían.

. *Derivación de direcciones* — los algoritmos de hash se utilizan a menudo en las blockchains como un medio para derivar direcciones de billetera — p. ej., como se discute en la sección <<create-wallet>>.

. *Merkleización(((merkle)))* permite compactar grandes colecciones de elementos de datos en una estructura más pequeña, es decir, un árbol de Merkle, y aún así poder probar que un elemento de datos en particular está representado dentro del árbol de Merkle sin tener que almacenar todos los elementos de datos. La Merkleización se discute más adelante en la sección <<chapter8-marlowe-security>>.

. *Almacenamiento direccionado por contenido(((almacenamiento direccionado por contenido)))* — cuando se requiere hacer referencia a otra información o archivos (por ejemplo, desde un contrato inteligente), a menudo es útil referirse al archivo (o información) específico usando almacenamiento direccionado por contenido, que se refiere a dicha información/archivos usando un hash de su contenido. Al hacerlo, es posible determinar inmediatamente si los contenidos han cambiado, ya que la referencia para encontrar la información/archivo es un hash que debe coincidir con el hash calculado del contenido, lo que se puede hacer en cualquier momento. Además, dicho esquema de referencia permite la deduplicación, por ejemplo, si se hace referencia a los mismos datos de imagen dos veces, solo se necesita almacenar una versión del archivo, ya que ambas referencias se resolverían al mismo hash.

==== Firmas digitales y técnicas de cifrado

. *Generación de billeteras* — los pares de claves pública/privada(((clave privada))) se generan usando algoritmos de cifrado asimétrico(((cifrado asimétrico))), que proporcionan la base para identidades/billeteras que se pueden generar sobre la marcha de manera descentralizada.

. *Firma/prueba y verificación de transacciones* — una vez que un usuario tiene una billetera (al generar un par de claves pública/privada), puede crear y firmar transacciones y probar a cualquiera que la transacción es válida y fue generada usando la billetera respectiva. Por ejemplo, cuando alguien quiere transferir fondos de su billetera a otra persona, los detalles de la transacción se firman digitalmente usando la clave privada de la billetera. A partir de entonces, cualquier otra persona puede verificar que la transacción fue iniciada por la billetera respectiva, ya que pueden verificar la firma digital contra la clave pública de la billetera.
